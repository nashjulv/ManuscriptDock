# 本地论文版本库

- 状态：MVP 已实现
- 产品名称：论文版本库 / Manuscript Version Library
- 核心原则：像时间线一样简单，像本地代码仓库一样可追溯

## 1. 为什么不是普通“本地保存”

普通文件夹只能看到若干文件名，无法可靠回答：当前稿是哪一版、某次修改改变了什么、投稿时使用了哪一版、恢复旧稿是否覆盖了后续工作。ManuscriptDock 因此把每篇论文建立为一个本地版本库，而不是把文件散放在应用目录中。

面向作者的界面不暴露 commit、HEAD、checkout 等 Git 术语，只保留五个直接动作：

1. 选择修改后的稿件；
2. 写一句可选的版本说明；
3. 保存为新版本；
4. 选择任一旧版与当前稿比较；
5. 把旧版恢复成一个新的当前版本。

## 2. 版本语义

- `v1` 是首次导入的不可变原稿；
- 每次有真实内容变化时，创建连续编号的新版本；
- 内容指纹与当前版本相同的文件不会形成重复版本；
- 新版本必须保持相同源文件类型，DOCX、PDF、TEX 之间的格式转换属于投稿输出，不混入作者修订历史；
- 每个版本记录父版本、创建时间、内容指纹、文件元数据、说明和来源类型；
- “恢复 v1”不会回退或删除 v2，而是以当前版本为父节点创建新的 v3，并记录它来自 v1；
- 历史版本和原始输入始终只读。

这套语义既保持线性时间线的易懂，也保留了未来形成分支、投稿版本和返修版本图谱所需的父子关系。

## 3. 界面结构

版本库是原稿后的第二个工作阶段：

```text
原稿 → 版本 → 结构 → 目标 → 格式 → 检查 → 投稿包 → 知识体
```

操作面只保留一个主操作“选择修改后的稿件”或“保存为 vN”。下方时间线倒序显示版本号、版本说明、文件名、时间、来源和当前状态。选择旧版本后才渐进显示“恢复为新版本”。

证据面显示所选旧版与当前版之间的确定性差异：

- 标题前后值；
- 词元、图、表的数量变化；
- 新增和移除的章节；
- 新增和移除的投稿声明；
- 两个版本的完整 SHA-256 内容指纹；
- 本地执行和未发生外部传输的边界。

当前比较不使用 AI，因此不会把语义推测包装成确定事实。DOCX、PDF 与 TEX 的比较能力受各自可确定提取层限制。

## 4. 本地存储模型

每篇论文仍使用独立 UUID 工作区。清单升级到 schema v2，并兼容读取既有 schema v1 工作区。

```text
projects/<workspace-id>/
├── manifest.json
├── audit.jsonl
├── source/original.<ext>          # v1，永久保留
├── versions/v0002/manuscript.<ext>
├── versions/v0003/manuscript.<ext>
├── analysis/
└── outputs/
```

WebView 只接收安全的版本元数据和比较结果，不接收真实文件路径。文件选择、复制、只读权限、指纹、清单替换、恢复和比较全部由 Rust 可信层负责。

审计事件至少记录：`workspace_created`、`version_created`、`version_restored`、`structure_analyzed` 和 `readiness_evaluated`。

## 5. 与知识体的关系

论文版本库不是独立于知识体的附加工具，而是“来源”要素的版本基础。后续结构、Claim、证据、审稿意见和投稿包必须指向明确的论文版本，不能笼统指向“这篇论文”。

未来与 PWC 同步时，以选定版本和授权对象为单位投影，不默认上传整个本地版本库。

## 6. 与投稿优化修订台的关系

[投稿优化修订台](submission-revision-desk.md)记录具体修改、修改依据和作者确认，本地版本库
记录修改完成后形成的不可变稿件及其父子关系。修订台是具有语义的版本生产入口，版本库
则接受应用内修订和外部编辑器导入的全部版本，不建立第二套历史。

修订台保存修改时必须创建新版本，不能覆盖当前稿；版本库恢复旧稿时同样创建新版本，
不能反向改写已经确认的修改记录。

## 7. 当前边界与后续演进

MVP 已实现连续版本、内容去重、时间线、结构化比较和安全恢复。投稿优化修订台现在可以
把 TEX 标题、摘要、关键词和 DOCX Title 样式标题保存为新版本，并在对应版本目录记录
结构化修改集。尚未实现：

- 直接打开外部编辑器及工作副本变更监听；
- 逐段或逐词红线比较；
- 命名分支、合并和冲突处理；
- 将某个版本标记为“预印本”“初投稿”“返修一轮”等里程碑；
- 附件、回复信和审稿意见随版本共同演进；
- 用户选择目录的版本库导出、备份与迁移。

演进顺序应优先增加版本里程碑和 DOCX/TEX 正文红线比较，再考虑向作者暴露分支概念。
