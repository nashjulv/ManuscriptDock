# 投稿优化修订台

- 状态：R1 首个可用切片已实现
- 产品名称：投稿优化修订台 / Submission Revision Desk
- 核心原则：只改投稿所需内容；每次修改有依据、有差异、有版本、可撤回

## 1. 产品定位

ManuscriptDock 需要提供导入论文后的优化编辑能力，但不应成为另一个 Word、Overleaf
或通用富文本编辑器。产品要解决的是作者在投稿准备阶段的闭环断裂：系统发现问题后，
作者不必离开应用反复修改、重新导入并猜测检查结果是否仍然有效。

投稿优化修订台位于“检查问题”和“保存新版本”之间：

```text
导入原稿 → 确定性检查 → 查看依据 → 接受或手动修改 → 对比差异
        → 保存为新版本 → 重新检查 → 生成投稿包 → 沉淀知识体
```

它是面向投稿任务的结构化修订环境，而不是从空白页开始的写作工具。自动排版仍是用户
进入产品的抓手；修订台把一次性检查变成可持续迭代；本地版本库则让每次迭代可以安全
返回和追溯。

## 2. 首期处理范围

首期只处理能够明确定位、验证和回写的投稿相关内容：

- 标题、副标题和短标题；
- 摘要、结构式摘要字段和关键词；
- 作者、单位及其对应关系；
- 章节标题、顺序和必要章节；
- 图表题注、编号和正文交叉引用；
- 资助、伦理、利益冲突、数据可用性、作者贡献和 AI 使用声明；
- 参考文献的可确定格式与完整性问题；
- 目标规则要求的字数、摘要结构和材料清单；
- Cover Letter 等可从已确认信息生成的投稿附件。

首期不包含：

- 通用富文本写作、自由排版和完整 Word 功能；
- 页眉、页脚、分栏及每本期刊的最终印刷版式复刻；
- 复杂公式创作、重型图片处理或数据分析；
- 多人实时协作；
- 未经作者确认的自动改写或静默覆盖。

## 3. 不同源格式的策略

| 源格式 | 修订方式 | 输出边界 |
| --- | --- | --- |
| DOCX | 提取统一结构，在受支持字段和区块上编辑 | 生成新的 DOCX 版本，保留原稿 |
| LaTeX | 定位源文件与结构节点，生成可审阅补丁 | 写入新版本；复杂内容可继续在外部编辑器处理 |
| 文本型 PDF | 只读证据、批注和问题定位 | 不把 PDF 反向改造成可信源稿，提示提供 DOCX/TEX |
| 扫描 PDF | OCR 候选文本与位置供作者确认 | 不自动生成被视为可信修订稿的正文 |

系统应优先保持原格式中的未知内容，不为了统一编辑而丢弃公式、域、批注、样式或宏。
当无法保证往返一致性时，应退回“定位问题 + 导出建议 + 外部编辑”的安全路径。

## 4. 修改不是覆盖，而是结构化补丁

修订台不直接覆盖整篇原稿。每轮修改形成一个 `RevisionSet`，其中包含若干可独立确认的
修改项：

```text
RevisionSet
├── baseVersion              # 修改所依据的论文版本
├── changes[]
│   ├── targetNode           # 标题、摘要、声明、段落或引用等稳定节点
│   ├── before / after       # 修改前后内容
│   ├── reason               # 为什么修改
│   ├── basis                # 作者修改 / 确定性规则 / AI 建议
│   ├── source               # 规则来源、模型记录或作者操作
│   └── status               # 候选 / 已接受 / 已拒绝
└── outputVersion            # 接受修改后生成的不可变新版本
```

确定性修复、AI 建议和作者直接修改必须使用不同标识。AI 只能生成候选补丁，不得静默接受；
规则也不能在无法保证语义安全时自动改写作者内容。保存时始终生成派生版本，原稿和历史
版本继续只读。

## 5. 界面结构

延续 ManuscriptDock 的双面板和渐进披露方式：

- 左侧操作面：问题列表、可编辑字段、规则来源、接受、拒绝和手动修订；
- 右侧证据面：原文定位、修改前后、红线差异和目标格式预览；
- 底部只保留一个主要动作：`保存为新版本`；
- 保存前显示将写入的修改数量、基础版本和目标版本；
- 保存后自动重新执行受影响的确定性检查，不沿用已经失效的旧结论。

默认只展示当前任务所需的字段，不同时铺开整篇论文。作者可以回到外部编辑器继续深度
写作；ManuscriptDock 负责重新识别变化并建立新版本。

## 6. 与本地论文版本库的分工

两项能力共同组成“安全修订闭环”，但职责不同：

| 能力 | 负责回答 |
| --- | --- |
| 投稿优化修订台 | 改了什么、为什么改、依据是什么、作者是否接受 |
| 本地论文版本库 | 哪个文件是当前版本、由哪个版本派生、如何比较和安全恢复 |

修订台是语义明确的新版本生产入口；版本库是不依赖编辑方式的不可变历史。作者从外部
编辑器导入的修改和修订台生成的修改都进入同一版本时间线，不建立两套版本事实。

## 7. 与学术知识体的关系

每个已接受修改都应成为知识体中的可追溯变更事件，并至少关联：

- 被修改的稳定节点或 Claim 五元组要素；
- 修改前后的论文版本；
- 作者、规则或模型这一责任来源；
- 规则依据、证据位置和确认状态；
- 受影响的投稿目标、检查结论和输出快照。

因此，修订台不仅生成“更适合投稿的文件”，还记录知识体为什么演化。论文正文版本与
Claim 要素版本不应简单等同：一次格式修复可能只产生新的稿件版本，而命题、条件、证据、
来源或状态发生实质变化时，才分别推进对应要素的版本。

## 8. 开发顺序与验收边界

### R1 — 结构化元数据与声明

- 已实现 TEX 标题、摘要和关键词的安全定位、修改与回写；
- 已实现 DOCX `Title` 样式标题的安全回写，其他 DOCX 字段保持只读并明确提示边界；
- PDF 保持只读，不从版面文本反向生成可信修订稿；
- 已展示出版社投稿要素、修改前后和作者修改来源；
- 接受修改后生成新的不可变版本，并在版本目录保存 `revision.json` 修改集；
- 作者单位、投稿声明、保存后自动重跑受影响检查仍待后续 R1 切片。

### R2 — 正文区块与引用

- 支持章节、题注、交叉引用和参考文献的定位修订；
- 提供段落或词级红线；
- 处理原稿已变化时的补丁冲突，而不是覆盖新内容。

### R3 — DOCX / TEX 安全往返

- 验证受支持 DOCX 结构的往返保真；
- 为 LaTeX 多文件项目提供可审阅源代码补丁；
- 对无法安全回写的内容明确降级为外部编辑流程。

首个可交付版本的验收不是“能编辑整篇论文”，而是作者可以对一个真实投稿问题完成：
查看依据、修改或接受、检查差异、保存新版本、重新验证，并在版本库和知识体中找到完整
来源链。
