# 知识体问答与作者自带模型

- 状态：MVP 已实现
- 日期：2026-08-25

## 1. 产品目的

知识体问答不是普通论文聊天，也不以一次回答替代知识体。它让作者围绕已经固化的
`KnowledgeBodyRecord` 提出认可、疑问或挑战，并把问题、模型回答、对象范围、版本、
来源锚点和模型身份保存为可追溯的研究记忆。

界面位于知识体空间图下方，分为“我的问答”和“外部反馈”两层：

- 我的问答：作者使用自己配置的大模型，询问整个知识体或 Claim、Scope、Method、
  Result、EvidenceRelation、SourceAnchor、AIReviewReport、Provenance。
- 外部反馈：为未来获授权的读者保留认可、疑问和挑战入口。当前版本不开放网络入口，
  不生成或伪造外部反馈。

## 2. 三槽模型设置

模型调度固定提供三个有序槽位：

1. 主模型；
2. 备选模型 1；
3. 备选模型 2。

作者分别填写提供方名称、OpenAI Chat Completions 兼容地址、模型名称和 API Key，并可
独立启用或停用槽位。问答按上述顺序尝试；连接失败、超时、非成功状态、无法识别的响应
或空回答会触发下一个可用槽位。任意槽位成功后停止继续请求。

提供方错误会转换为带恢复动作的本地提示：401/403 指向 Key 或权限，402 指向余额或计费，
404 指向 API 地址，422 指向模型名或兼容参数，429 指向频率/账户限额，5xx 指向提供方故障
或繁忙。失败后仍继续尝试下一可用槽位；没有备选成功时才汇总显示。DeepSeek 含义以其
[官方错误码](https://api-docs.deepseek.com/zh-cn/quick_start/error_codes/)为准。

“启用”只表示作者希望使用该槽位，“可用”还必须同时满足：提供方、API 地址、模型名
完整，API Key 已保存到系统凭据库，并且设置已成功提交。界面逐槽显示未启用、配置不完整、
地址错误、缺少 Key、保存后可用或已启用，不再用一个禁用按钮隐藏原因。没有可用模型时，
问答主按钮会直接打开模型设置。

DeepSeek 提供一键官方配置，按[官方首次调用说明](https://api-docs.deepseek.com/zh-cn/)，
当前 OpenAI 兼容参数为 `https://api.deepseek.com` 与 `deepseek-v4-flash`。
`https://api-docs.deepseek.com/zh-cn` 是文档网站而不是 API，前后端都会明确拒绝把它保存为
已启用模型。预设不包含 Key，作者仍须自行输入并保存。

DeepSeek V4 默认启用高强度思考模式，思考内容与最终正文分别返回。知识体问答需要稳定、
可保存的最终正文，因此 Rust 对官方 `api.deepseek.com` 的 Chat Completions 请求显式设置
`thinking.type = disabled`，并提供 2400 个输出 token；其他 OpenAI 兼容端点不接收这个
提供方专属参数。响应解析接受字符串或文本分段，但内部 `reasoning_content` 永远不作为
答案展示或写入问答账本。若提供方达到输出上限或只有推理而无最终正文，应用显示具体原因
并继续尝试下一个启用槽位。

远端地址必须使用 HTTPS；只有 `localhost`、`127.0.0.1` 和 `::1` 允许 HTTP，以兼容作者
自建的本机模型服务。

## 3. 密钥与网络边界

- macOS 使用 Keychain，Windows 使用 Credential Manager；设置文件只保存非敏感元数据。
- 已启用槽位必须具有新输入或既有的 Key；勾选删除 Key 时不能继续把同一槽位保存为启用，
  防止出现“配置已保存但永远无法调用”的假启用状态。
- WebView 只把作者当次输入的 Key 交给窄范围 Rust 命令，Rust 不把明文 Key 返回界面，
  不写入工作区、日志、问答记录或 Git 仓库。
- 只有作者点击“询问知识体”才发起模型请求；后台不自动上传，也不周期调用。
- 每次调用只发送脱敏后的当前问题和最小知识体投影：记录 ID/哈希、快照版本、作者确认的
  学科、稿件版本、已提取标题/摘要/章节、版本化核心对象引用，以及五部分服务架构中的能力
  契约、知识边界、运行时政策和权利信誉引用。Rust 在网络出口删除结构报告和本地投稿档案中已知的作者姓名、邮箱、
  电话、长数字身份标识和本机路径；作者列表、源文件和本机路径不发送。
- 模型错误只记录槽位和概括性原因，不保存响应正文、认证信息或供应商调试载荷。

## 4. 可追溯对象

`KnowledgeInquiryRecord` 是不可变问题记录，固定：

- 当前知识体记录 ID、完整哈希和快照版本；
- 发问方（作者或未来外部读者）；
- 立场（认可、疑问、挑战）；
- 目标对象与原始问题；
- 时间、传输状态和自身记录哈希。

`KnowledgeAnswerRecord` 是不可变回答记录，固定：

- 对应问题、知识体记录和回答时间；
- 实际成功的主/备选槽位、提供方和模型名称；
- 回答正文、来源锚点、传输状态和自身记录哈希。

模型失败时，问题仍保存在本机并显示“尚未形成回答”。知识体重新分类或形成新版本后，
新问答绑定新记录；旧账本仍保留为历史，不混入当前知识体。

## 5. 写回原则

模型回答是对已知投影的说明或建议，不是科学真理，也不能自动改写 Claim、Scope、Method、
Result 或 EvidenceRelation。后续若把回答转化为候选对象，必须经过作者确认并产生新的对象
版本、来源关系和 Provenance。

schema v2 将模型定义为可替换的交互运行时，而不是知识本身。模型必须先检查
`CapabilityContract` 的输入、输出、前置条件和拒绝条件；超出知识边界、证据不足、能力仍为
`planned` 或未获单次外发授权时必须拒绝。RightsPolicy 与 ReputationRecord 只作为当前
版本引用进入投影，模型不得把引用量或外部评价反写为论文内容。

## 6. 外部反馈后续合同

外部入口开放前至少需要：公开快照选择、作者授权范围、提问者身份或匿名政策、限流与滥用
治理、撤回政策、模型成本归属、问题和回答的公开范围，以及独立传输审计。外部提问不能
读取本地未发布稿件，也不能因模型回答反向修改作者主本。
