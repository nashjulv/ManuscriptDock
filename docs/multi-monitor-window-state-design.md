# 多显示器窗口恢复与适配方案

- 日期：2026-09-07
- 状态：用户确认后已实施；产品版本仍为 V0.49。实施细节与验证边界见第 9 节。
- 基线：提交 `3c3d5f4`，Tauri 2.11.5、tauri-plugin-window-state 2.4.1。
- 范围：正常窗口、最大化、跨屏拖动、显示器断连、缩放变化和启动恢复。macOS 优先，保留 Windows 平台适配边界。

## 1. 研究时的基线与问题

研究基线 `3c3d5f4` 只有基础尺寸记忆，没有完整的多显示器适配。此前原生验证证明了同一屏幕上的关闭/退出再打开，不代表混合 DPI、多屏热插拔或断开外屏后的恢复已经通过。以下问题描述该基线；第 2–7 节保留获准实施的设计。

基线的 `apps/desktop/src-tauri/src/lib.rs` 只开启插件的 `SIZE | MAXIMIZED`。检查当时锁定的 2.4.1 源码发现：

- 普通窗口的 `inner_size()` 以物理像素保存；恢复直接使用 `PhysicalSize`。
- 没有保存来源屏幕、来源缩放比例、来源工作区域或每屏独立偏好。
- 没有把恢复尺寸限制到目标屏幕可用区域；760 × 620 的配置只是最小尺寸。
- 未启用位置恢复，能避免我们主动套用旧屏幕绝对位置，但不能解决尺寸过大。
- 当前插件配置下，移动事件不会触发应用自己的适配策略；插件也未处理 `ScaleFactorChanged`。
- 在正常退出时写盘；不能把强制终止后的恢复视为已保证行为。

Tao 的 macOS 层会处理 backing scale 变化，按窗口当前逻辑尺寸生成新的像素尺寸，因此普通拖动的基础缩放不等于完全失效。但这不包含产品级的屏幕适配和恢复策略。

Apple 对 `constrainFrameRect` 的说明是：让窗口顶部位于屏幕内，并在适用情况下限制高度；宽度与水平位置不受此约束影响。因此不能推断系统会把所有超大窗口完整放回小屏幕。

上游 #3521 报告在插件 2.4.1 和混合 DPI 的 macOS 环境下，启动早期缩放比例尚未稳定时可能把保存的物理像素当成错误的逻辑尺寸，导致恢复后变大。它是尚未关闭的用户缺陷报告，与本地实现路径相关，但不是 ManuscriptDock 已实机复现的结论。

## 2. 三类屏幕数据必须区分

1. 面板分辨率：例如 2560 × 1440、3840 × 2160。
2. 逻辑工作空间：应用实际排版使用的点/逻辑像素，受系统缩放影响；不是屏幕的物理厘米大小。
3. 当前可用区域：排除 Dock、菜单栏和刘海遮挡等系统保留空间后的范围。

窗口恢复以逻辑内容尺寸为用户偏好，适配以目标屏幕当前可用区域为边界。不能仅凭“2K”或“4K”选尺寸，也不能把全桌面的全局坐标一律除以某一个屏幕的缩放比例。

例：1200 逻辑像素宽的窗口，在 2× backing scale 下可能记录为 2400 物理像素。若恢复到 1× 屏幕并直接使用 2400，申请的逻辑宽度就变成 2400。反方向也可能变小。这是单位转换示例，最终窗口尺寸仍可能受到系统约束。

## 3. 建议的用户体验

| 情况 | 建议行为 |
| --- | --- |
| MacBook 内屏拖到外接屏 | 保留逻辑内容宽高；交给系统处理清晰度，不因外屏更大自动放大窗口或改字号。 |
| 外接屏大窗口拖回较小内屏 | 拖动结束且归属屏幕稳定后，只缩小超出可用区域的维度；把标题栏与窗口边界放到可操作范围。 |
| 在外屏关闭，断开外屏后重开 | 选择仍可用的目标屏幕，优先使用该屏历史尺寸；没有历史时使用最近偏好并限制到当前工作区。 |
| 重新连接外屏 | 正在使用的窗口不主动跳回外屏；以后在该屏启动可恢复该屏偏好。 |
| 拖回曾经用过的大屏 | 不自动放大当前窗口；保留该屏先前手动设置的尺寸供下次启动使用。 |
| 在同屏调整系统缩放或分辨率 | 重新获取可用区域；保持逻辑尺寸，只有容纳不下时缩小。 |
| 外屏被拔掉、扩展坞断连或合盖切换 | 等系统完成显示配置变化，再选择仍在线屏幕并修正；不抢焦点、不抢走用户正在拖动的窗口。 |
| 窗口跨在两个屏幕之间 | 拖动中不干预；落定后确定归属屏幕，避免在边界反复放大缩小。 |
| 最大化后退出 | 保存正常尺寸与最大化状态；下次在选定的可用屏幕上最大化，不套用原屏的像素尺寸。 |
| 全屏、最小化、Windows 贴靠 | 不把这些临时几何当作普通窗口偏好；全屏与贴靠期间不执行普通窗口修正。首版不恢复全屏或贴靠布局。 |

建议不开新的设置面板，默认按上述规则工作。系统字号和“更小 / 默认 / 更大”阅读设置不随屏幕自动改变；首页继续按实际逻辑视口执行隐藏、比例、固定三段布局。

## 4. 尺寸、位置与屏幕选择

### 4.1 尺寸限制

保存内容区宽高；做可见性判断时使用外框，包括标题栏和系统边框。不能把系统工作区高度直接当作内容区高度，也不能硬编码标题栏的像素高度。

建议普通窗口边缘预留约 12 个逻辑像素，作为可调整的内部常量。最大化交给系统，不套用该留白。

计算顺序：

1. 实时读取目标屏工作区域，使用该屏的缩放因子转换尺寸。
2. 获取实际装饰边框占用，计算可用内容区上限。
3. 每个维度独立限制到上限，不强制保持窗口宽高比。
4. 正常最小尺寸仍为 760 × 620；若工作区本身更小，临时降低该次窗口最小限制到可容纳范围，优先保证窗口可操作，正文通过响应式与滚动适配。
5. 如果目标工作区极端小于现有前端 320px 最小宽度，不宣称完整布局可用；至少保留系统关闭与调整窗口入口，作为异常显示配置处理。

独立限制宽高能避免“只因高度不够，就把本来足够宽的工作台也同比缩小”。

### 4.2 位置处理

运行中跨屏时保留用户落点，只做必要的越界修正；不在每次移动后居中。启动时若有可信的目标屏锚点则恢复，否则在目标可用区域内居中。

位置保存为相对于该屏可用区域的局部逻辑偏移或归一化锚点，避免把旧屏幕在全桌面上的绝对坐标原封不动套到新排列。macOS 平台适配层可直接使用 AppKit 的点坐标；跨平台换算必须由同一适配层完成，不混用不同屏幕的物理坐标空间。

### 4.3 目标屏幕和身份

启动优先选最近使用且仍能可靠匹配的屏幕；缺失时使用系统选择的当前屏幕，再回退到主屏。仅剩内屏时自然回到内屏，不默认挑最大的屏幕。

Tauri 的屏幕名称不能作为唯一身份：同型号显示器可能重名，屏幕排列和系统显示 ID 也可能变化。macOS 方案需研究平台显示 UUID 的匹配稳定性，Windows 使用对应的设备路径标识；本地只存匹配所需的散列或内部标识，不上传。

尺寸、比例、名称等只用于辅助判断，不作为强身份。相同型号或连接方式变化导致匹配不唯一时，放弃精确每屏恢复，执行安全尺寸回退，不套用不确定的位置。换口、扩展坞和镜像显示必须纳入验证。

## 5. 状态持久化与事件管理

建议建立 Rust 自有 `window_geometry` 模块，取代当前插件对 `main` 窗口的自动保存/恢复，避免两套逻辑同时改尺寸。仅添加一个配置开关或在插件恢复后再修正，无法完整解决来源比例缺失、缓存覆盖与恢复时序问题。

建议状态包含：schemaVersion、正常窗口逻辑内容尺寸、普通/最大化模式、最后屏幕标识、每屏偏好、可选局部锚点、上次工作区与比例快照（仅用于诊断和合理性校验）。

每屏状态区分两种尺寸：

- **偏好尺寸**：用户在该屏主动调整并稳定后的结果。
- **有效尺寸**：系统变化或应用安全修正后，当前实际使用的尺寸。

自动缩小只更新有效尺寸，不覆盖偏好尺寸。窗口第一次到达某屏且该屏没有偏好时，可以建立初始记录；已有偏好不因一次自动缩小或普通移动被替换。关闭保存状态和最后屏幕，但不无条件把当前有效尺寸写成偏好。

不能只靠收到 `Resized` 就认定用户手动调整。应结合原生交互起止、显示配置变更、应用自己发起的尺寸操作标记和稳定期判断；无法明确归因时保留已有偏好。

事件机制建议：

1. 启动阶段先读状态、确定目标屏和合法尺寸，再显示窗口；在应用显示与尺寸归属稳定前禁止写入偏好。准备失败时显示受保护的默认窗口，不能无限等待或一直隐藏。
2. 监听 Tauri 的 Moved、Resized、ScaleFactorChanged 和 Focused；不只监听 DPI，因为两块屏幕的比例可能相同。
3. macOS 补充 AppKit 屏幕配置变更与窗口换屏通知，覆盖断连、缩放、唤醒后的重新检测；当前 Tauri 窗口事件没有完整的显示器热插拔通知。
4. 合并短时间事件，初步采用 300ms 稳定窗口；但防抖不是拖动结束的充分证据，必须等待原生交互结束或确认没有活动拖动，避免用户停顿时被抢窗口。
5. 对程序发起的尺寸和位置变更添加恢复/修正标记及操作序号，回读实际几何后结束；陈旧事件不得覆盖新的操作。超过容差才调整，限制每轮修正次数，防止递归与抖动。
6. 原子写盘，正常关闭再刷盘；拖动/手动调整稳定后也防抖保存，降低强制退出丢失最近设置的概率。写入失败不阻断启动，不把错误缓存替换掉。

Tauri 的 `prevent_overflow` 可作为首次创建窗口的补充保护，但本地源码显示它作用于创建过程，不能替代运行中跨屏与插件恢复后的适配。

## 6. 旧记录迁移

现有 `.window-state.json` 没有保存来源 scale factor 或屏幕身份。仅凭旧宽高无法可靠判断它来自 1× 还是 2× 屏幕，因此不能直接把旧数字改标为逻辑像素，也不能用启动时当前屏幕的比例冒充来源比例。

建议升级后一次性回退到安全的默认逻辑尺寸 1180 × 780，并按当前工作区限制；旧文件保留为迁移备份、不直接继续应用。之后用户调整即建立新格式记录。若将来明确取得可信的来源信息，才考虑受控迁移；首版不做猜测。

## 7. 实施拆分与验收

建议分两层实现，不能只修启动而忽略运行中跨屏：

1. **基本保护层**：逻辑尺寸记录、启动工作区限制、恢复时序、普通与最大化分离、运行中跨屏/断屏保护、旧记录安全回退。
2. **偏好体验层**：可靠屏幕身份、每屏偏好、局部位置锚点、自动修正与手动调整的持久化隔离。

纯函数测试使用合成显示拓扑，验证混合 DPI、负坐标、纵向屏幕、菜单/Dock 留白、边框换算、无屏幕/读取失败、工作区小于最小尺寸、状态损坏及不产生尺寸增长循环。尺寸适配应幂等，重复修正不能持续缩小或放大。

原生必测矩阵：

| 维度 | 必测场景 |
| --- | --- |
| 屏幕 | Retina 内屏 ↔ 1× 2K；Retina 内屏 ↔ 使用系统缩放的 4K；两块相同缩放比例的屏幕 |
| 移动 | 小到大、大到小、超宽窗口、只超高窗口、停在边界、跨屏后再拖回 |
| 启停 | 外屏关闭后断开重开、外屏最大化后断开重开、连续关闭重开至少 10 次 |
| 拓扑 | 外屏在左侧/上方、竖屏、切换主屏、镜像、换接口、扩展坞重连、合盖与开盖 |
| 系统 | 修改缩放、修改分辨率、Dock 换边/隐藏、睡眠唤醒、系统全屏切换、Windows 贴靠 |
| 内容 | zh-CN/en × 三档字号；首页三段布局、模型设置弹窗、稿件工作区和底部操作 |

通过标准：标题栏可操作；安全恢复后的普通窗口完整位于可用区域；拖动中不抢窗口；连续重启逻辑尺寸不累积漂移；自动缩小不污染偏好；不自动修改阅读字号；无恢复闪烁循环或持久化事件风暴。无法实测的硬件组合应明确列为未验收。

Internationalization review：功能不新增 UI 文案或 WebView 消息；内部失败使用稳定诊断码，不输出稿件信息或路径。zh-CN/en 使用同一几何策略，使用手册已同步中英说明；原有双语前端测试通过。完整多屏 × 双语 × 三档字号的原生矩阵仍需实机验收。

## 9. 实施记录与验证边界

代码位于 `apps/desktop/src-tauri/src/window_geometry/`，分为纯策略、持久化、控制器及平台适配层。移除 `tauri-plugin-window-state`，由一个管理器负责主窗口，保持 V0.49 / 0.49.0 与正式应用标识不变。

- macOS 直接使用 AppKit 点坐标、`NSScreen.visibleFrame` 与实际内容/外框换算；通过显示 UUID 的 SHA-256 散列区分屏幕。监听显示配置、窗口换屏和 live-resize 结束通知。
- Windows 使用原生工作区、有效 DPI 和设备接口路径散列，在适配层完成局部物理/逻辑换算。子类消息区分移动与手动调整；动态解析贴靠查询以兼容旧系统，缺失时保守比较正常恢复框尺寸。
- 屏幕身份缺失或重复时不保存该屏精确位置；保留全局安全尺寸回退。最多 16 份每屏记录，淘汰顺序跨启动延续。
- 使用 300ms 稳定期、800ms 程序调整保护期及每轮最多两次修正；原生通知配合每 500ms 重新采样，涵盖 Tauri 未提供专门事件的拓扑变化。启动先隐藏恢复，最迟约 2 秒尝试显示；读取屏幕信息失败时仍可显示默认窗口，后续有有效信息再恢复。显示调用失败会重试。
- 新状态为 `window-geometry-v1.json`，只持久化偏好、有效尺寸、锚点、模式和屏幕散列；工作区与比例保留在运行时快照，未增加诊断数据落盘。原子临时文件替换，串行版本检查阻止旧队列覆盖退出刷盘；损坏、未来格式或超出 256KiB 的记录安全回退。
- 全屏、最小化和 Windows 贴靠不写入普通尺寸；立即关闭可以刷入刚完成的手动调整；调整后最大化不污染正常偏好。自动缩小与普通移动不覆盖已有偏好。
- 其他平台保留安全启动适配层，但没有可靠原生交互信号时不推断手动尺寸或在运行中移动窗口；不属于本产品本轮支持和验收的 macOS/Windows 范围。
