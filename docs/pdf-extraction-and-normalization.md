# PDF 提取与规整方案

## 结论

ManuscriptDock 采用“文档与页面分类 → 原生对象提取 → 缺失对象识别 → 有来源合并”的本地链路，而不是导入后立即对整篇论文做 OCR。PDF 源稿保持不可变；原生文字、公式区域和表格结构优先，只有对应对象无法读取或低可信时才进入识别候选。

这里的“对象识别”不是一种万能 OCR：普通文字使用中英文文字 OCR，公式需要公式识别模型，表格需要表格结构识别。三者不能互相替代。

## Pandoc 评估

[Pandoc](https://pandoc.org/MANUAL.html)适合在 Markdown、DOCX、LaTeX、HTML 等结构化格式之间转换，也适合从这些格式生成 PDF。它没有 PDF 输入 reader，因此不能承担已有 PDF 的标题、作者、摘要、多栏阅读顺序或表格恢复。

结论：Pandoc 不作为 PDF 提取器。后续它可以作为作者确认后的规范化稿件在 DOCX、LaTeX、Markdown 之间转换的可选工具，但不得把 PDF 版面反推结果包装成无损源稿。

## pdf-inspector 评估

[Firecrawl pdf-inspector](https://github.com/firecrawl/pdf-inspector)的默认 Rust 构建使用 MIT 许可，不包含模型或外部服务，适合 Tauri/Rust 后端。它提供：

- TextBased、Scanned、ImageBased、Mixed 分类和置信度；
- CID/Type0、ToUnicode CMap 和异常编码检测；
- 字体、坐标、多栏阅读顺序、标题层级和表格感知的 Markdown；
- `pages_needing_ocr` 和逐页 OCR 原因；
- 可选的 PDFium、ONNX Runtime、PP-OCRv6 OCR 链路。

首轮只启用默认纯 Rust 能力。可选识别 feature 会引入平台动态库、模型缓存、安装包体积、CPU/内存管理和模型下载授权，因此不能在依赖未随安装包交付时伪装成可用功能。

## V1.1 执行链路

1. Rust 后端只读取不可变 PDF 快照，先识别整篇属于 `TextBased`、`Scanned`、`ImageBased` 或 `Mixed`，并记录置信度。
2. 同一次安全加载中继续做逐页分类，标出原生文字页、异常字体页、表格页、多栏页和需要补充识别的页。这里逻辑上先分类，工程上复用一次解析结果，避免重复读取整篇文件。
3. 对可读对象优先执行原生提取：文字使用字体映射、坐标和阅读顺序；表格使用单元格及版面关系；公式先保留所在区域和原始可读字符，不用普通文字 OCR 猜测 LaTeX。
4. Markdown 标题层级用于章节规整，Markdown 表格分隔行用于确定性表格计数；随后进入现有标题、作者、摘要、关键词、声明和图表推断。
5. 若布局感知结果不可用，依次回退 `pdf-extract` 字体映射和 `lopdf` 内容流，同时继续保留第一步的分类、表格页、多栏页和识别候选页。
6. 只有某页的某类对象无法读取或低可信时才路由到对应识别器；可读页面和可读对象不重复 OCR。
7. 合并时可靠原生块优先，识别结果只填补空缺区域；重叠候选去重，冲突项并存并等待作者确认，不允许识别结果静默覆盖原生内容。
8. 所有 PDF 结果继续保持 `limited`，防止把版面恢复误认为作者源结构。

## 对象级路由

| 对象 | 优先方法 | 失败后的补充识别 | 合并要求 |
| --- | --- | --- | --- |
| 普通文字 | 字体、ToUnicode、坐标与阅读顺序 | `zh_en_v1` 中英文文字 OCR | 原生文字优先；OCR 只补空区域 |
| 公式 | 可读字符、公式区域与版面锚点 | 独立公式识别模型 | 保留原图/区域；识别式必须待确认 |
| 表格 | 线条、单元格、坐标与 Markdown 表格 | 独立表格结构识别 | 保留行列关系，不降格为连续文本 |

结构分析 v5 已持久化文档分类、置信度、原生提取路径、表格页、多栏页、编码状态和需要补充识别的页。每个合并块未来至少记录 `page`、`bbox`、`object_type`、`source`、`extractor_or_model`、`confidence` 和 `needs_confirmation`。知识体中的 Claim、Method、Result 与 SourceAnchor 只能引用已确认的块和具体来源版本。

## 中英文 OCR 产品合同

普通文字 OCR 的首个正式语言档案固定为 `zh_en_v1`：简体中文、繁体中文、英文、数字和常见中英文标点，同一页面允许中英文混排，不要求作者手动切换语言。底层优先采用一个同时覆盖中英文的 PP-OCRv6 Small 识别模型，避免分别运行中文、英文模型造成重复框和阅读顺序冲突。该档案不承担数学公式和表格结构识别。

当前仓库尚未满足“可交付 OCR”的完整条件：项目固定 Rust 1.93，而 `pdf-inspector 1.17.0` 的 OAR OCR feature 需要 Rust 1.95；macOS 和 Windows 还必须随应用提供匹配的 PDFium、ONNX Runtime、许可证和校验清单。完成这些条件前，界面只能显示中英文 OCR 候选页，不能声称已经识别扫描文本。

正式启用必须同时满足：

- 只渲染缺失对象所在区域；若暂时只有页级坐标，则只渲染 `pages_needing_ocr`，不对整篇论文重复 OCR；
- PDFium、ONNX Runtime 和模型采用固定版本、SHA-256 校验和原子安装；
- 模型下载必须由作者明确触发，也允许完全离线目录；
- 每个对象块保留 `native`、`ocr`、`formula_recognition`、`table_recognition` 或 `fused` 来源和置信度；
- 识别结果只能成为待确认提取层，不能覆盖原稿或自动成为可信 Claim/证据。
- 语言档案、模型版本、置信度与每页来源必须进入结构分析记录。

## 验收标准

- 每份 PDF 先输出文档分类、置信度和逐页路由证据，再进行对象提取。
- 含 CID 字体或多栏文本的原生 PDF 优先使用布局感知提取。
- Markdown H1–H4 能稳定规整为标题和章节层级。
- 原生 Markdown 表格能够稳定计数；普通文字 OCR 不得覆盖已恢复的表格结构。
- 作者、摘要识别继续使用保守规则并显示确认提示。
- 混合 PDF 精确显示缺失对象及候选页，不再只给出整篇“可能需要 OCR”。
- 解析失败自动回退，不因新增解析器降低旧文件兼容性。
- 全过程不联网、不调用模型、不改动源文件。
