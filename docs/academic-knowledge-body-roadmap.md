# ManuscriptDock 学术知识体演进路线

- 状态：产品根目标 / 后续架构主线
- 日期：2026-08-24
- 适用范围：ManuscriptDock 个人端、PWC 机构端、AI 与发布连接器

## 1. 根本目标

ManuscriptDock 的根本目标不是只把论文排好版或检查一次投稿，而是让作者的论文在进入
审稿和传播网络之前，就形成一个由作者控制的学术知识体：

> 一个以不可变来源为基础，包含结构、论点、证据、引用、图表、声明、规则结论、评审、
> 返修和发布关系，具有稳定身份、版本、来源和权限的可计算学术对象。

自动排版是获取早期使用的抓手，投稿准备是第一条可信闭环，学术知识体是所有功能共同
沉淀的长期资产。

用户和付费主体仍然是作者、研究团队与机构；“服务知识体”描述的是平台持续管理的核心
对象，而不是削弱人的所有权和决定权。完整定义见
[学术知识体服务模型](knowledge-body-service-model.md)。

## 2. 为什么从投稿前开始

论文在投稿前已经具备最高的信息密度，但通常仍以 DOCX、TEX、PDF、附件和作者记忆的
形式分散存在。如果等正式发表后才结构化，将丢失投稿版本、审稿过程、作者决策和证据
演化。ManuscriptDock 应在作者仍掌握完整语境时完成第一轮本地结构化，并让作者逐步
决定哪些内容可以提供给模型、专业评审、预印本或机构网络。

## 3. 当前 MVP 已提供的地基

| 当前对象 | 在知识体中的作用 |
| --- | --- |
| 不可变源快照与内容指纹 | 事实来源、版本锚点和防篡改依据 |
| 本地论文版本库 | 连续稿件版本、父子来源、内容去重和安全恢复 |
| 确定性结构报告 | 标题、章节、图表、引用和声明的第一层语义 |
| 签名规则结论 | 带来源的投稿要求判断，不与作者事实混合 |
| 审计事件 | 谁在何时对哪个版本执行了什么操作 |
| JSON 与 HTML 输出快照 | 某次检查的可交付投影，而非知识体本体 |

当前结构报告仍是派生文件。下一阶段要建立正式的知识体清单，把这些对象通过稳定标识和
关系连接起来。

## 4. 核心对象边界

单一学术知识体不是论文摘要，而是围绕一个或一组 Claim 构成的、可追溯且可版本化的研究
记忆单元。主张的最小语义结构仍固定为：

> 主张 =〈命题、条件、证据、来源、状态〉

- `Claim` 是主张对象的核心身份，不是论文标题，也不是五元组之外的第六类数据；
- `命题` 描述具体声称为真的内容；
- `条件` 描述命题成立的范围、前提和约束；
- `证据` 连接支持、削弱或反驳命题的可定位材料；
- `来源` 记录原稿位置、引用、数据集或其他可追溯出处；
- `状态` 记录草拟、待确认、被支持、存在争议、被修订或撤回等生命周期状态；
- 五类要素各自拥有稳定标识和独立版本，不因其中一项更新而覆盖其他要素的历史。

正式单体以五部分服务架构组织：身份与版本、知识边界与证据、能力契约、交互与执行运行时、
验证权利与信誉。`ArtifactVersion`、`Claim`、`Scope`、`Method`、`Result`、
`EvidenceRelation`、`SourceAnchor`、`AIReviewReport`、`Provenance` 和
`KnowledgeBodySnapshot` 十类既有对象保留，并归入相应部分。Claim 五元组是 Claim 的
内部语义约束，不能代替整个知识体。完整定义见
[单篇论文知识体五部分服务架构](single-knowledge-body-service-architecture.md)。

首个 `AcademicKnowledgeBody` 模型至少需要：

- `identity`：论文稳定标识、标题和作者控制状态；
- `sources`：原稿、附件及其内容指纹，不可变；
- `versions`：工作版本、投稿版本、返修版本和发布版本；
- `nodes`：章节、段落、论点、证据、图、表、公式、声明和参考文献；
- `relations`：引用、支持、反驳、派生、回应、替代和发布映射；
- `assessments`：确定性规则结论、AI 候选建议和专业评审，三者明确分层；
- `changes`：作者修改、确定性修复和 AI 候选补丁，以及接受、拒绝和版本落点；
- `provenance`：来源位置、生成方式、模型或规则版本、时间和责任主体；
- `permissions`：本地、可向指定模型开放、可向 PWC 开放、可发布等授权范围；
- `projections`：投稿包、HTML 预览、预印本、JATS 或未来开放协议表示。

知识体清单只保存相对引用和内容身份，不向 WebView 暴露本机绝对路径。

`AIReviewReport` 必须作为独立版本对象存在。知识体快照固定引用具体报告版本，报告升级
保留旧版本且不自动推进 Claim 版本。多个知识体之间不共享一个无边界对象池，而通过有
成立依据、状态和独立版本的一等声明对象连接。完整协议见
[学术知识体关联网络模型](knowledge-body-network-model.md)。

当前投稿优化修订台已经为每个应用内新版本保存 `revision.json`，记录基础版本、输出版本、
修改前后、作者修改依据、接受状态和未发生外部传输。这是 `changes` 对象的首个落地格式；
后续正式知识体清单将注册这些修改集，而不是重新从文件差异猜测修改意图。

## 5. 三阶段演进

### 空间交互模型

知识体空间视图分为“单一知识体 / 两体关联 / 关联网络”三级。单体内部采用
“稳定 KnowledgeBody 外层边界 + 不可变内容快照内层边界 + Claim 十二面体 + 五个服务
星区”模型：

- Claim 位于缓慢转动的线框十二面体中心，表达同一主张核心可被多视角检查；
- 五条空间直线从 Claim 连接身份与版本、知识边界与证据、能力契约、交互运行时、验证权利与信誉；
- 十类论文对象继续在五个星区内显示自己的版本，不再作为同级球体平铺；
- RuntimeProfile 使用虚线表达可替换性，不与某个具体模型绑定；
- ReputationRecord 使用点线和双边界表达独立演进，内容信誉变化不改写固定快照；
- `KnowledgeBodySnapshot · Sx` 作为内层不可变边界，固定知识内容和能力契约的具体版本；
- `v0` 明确表示对象尚未正式建立，不能为了图形完整而虚构结果、方法或审核结论；
- 旋转只作用于中心十二面体，外围对象与版本号保持静止可读；系统启用减少动态效果时使用固定投影视角；
- 空间视图是核心对象清单的只读投影，不取代文本列表、版本记录和无障碍摘要。

未来一个 Claim 的某类要素出现多个版本时，应从“知识、边界与证据”星区进入版本历史，
而不是继续向首屏无限发散节点。

两体与网络层使用圆形边界保持每个知识体的身份与版本历史；跨体边的中点使用绿色菱形
表示 CitationAssertion、ClaimRelationAssertion、EvidenceRelation、
MethodRelationAssertion、ReproductionAssertion、AlignmentAssertion、VersionRelation
或 ClassificationAssignment。没有协议对象和成立依据的边不进入正式视图。

### K1 — 本地论文知识体

- 建立 schema-versioned `AcademicKnowledgeBody` 清单；
- 将现有源快照、结构报告、规则结论和审计事件注册为对象；
- 为结构节点生成稳定、可跨版本映射的标识；
- 将投稿优化修订台的修改集关联到基础版本、目标节点、依据和输出版本；
- 支持从对象关系生成投稿准备视图，而不是由 UI 拼接孤立结果。

### K2 — AI 可用但作者可控

- 已实现作者自带的一个主模型和两个有序备选模型，API Key 进入操作系统凭据库；
- 已为主动问答生成最小必要的知识体投影，并记录接收槽位、对象、快照、哈希和来源锚点；
- 已将问题和回答保存为不可变账本；回答不自动改写知识体，未来转为候选对象仍需作者确认；
- 后续补充逐次字段预览、费用预算、保留策略声明和公共问答授权；
- 用户配置的大模型与 PWC 专业评审保持不同信任域。

### K3 — 网络发布与机构协同

- 为预印本、期刊投稿和开放知识网络生成授权发布投影；
- 记录外部标识、平台状态、许可和撤回或替换关系；
- ManuscriptDock 作为个人数据端，PWC 作为机构规则、专业评审和治理中央端；
- 同步以对象、版本和权限为单位，不上传整个本地工作区作为默认行为。

## 6. 产品护栏

后续每个功能进入开发前必须满足：

1. 说明新增或消费哪些知识体对象；
2. 区分作者事实、确定性派生、AI 建议和专业判断；
3. 保留源版本和来源位置；
4. 不覆盖原稿或历史投稿快照；
5. 外发前生成可阅读的数据清单并取得针对该动作的授权；
6. 允许在不连接 PWC 或外部模型时继续使用本地核心能力；
7. 输出格式是知识体投影，不成为新的唯一事实源。
8. 应用内修订以可审阅补丁生成新稿件版本；只有 Claim 五元组要素发生实质变化时，才推进对应要素版本。

## 7. 下一开发决策

下一轮不应立刻扩张知识图谱界面，而应先在 Rust 核心中定义最小知识体清单和迁移策略，
把当前 M0–M3 的本地对象注册进去。随后让自动排版与目标期刊规则以知识体为输入和输出，
验证这条主线不会增加首屏复杂度。投稿优化修订台应作为知识体变更事件的首个主要写入端，
其范围和分阶段边界见[投稿优化修订台](submission-revision-desk.md)。
