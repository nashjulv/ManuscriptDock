# ManuscriptDock 产品设计总纲

- 状态：0.1 / 产品定义与体验基线
- 日期：2026-08-24
- 产品名：ManuscriptDock V0.15（安装标识保持 `ManuscriptDock`）
- 中文名：投稿舱
- 当前版本：V0.15
- 产品类别：本地论文投稿工作台

## 1. 一句话定义

> ManuscriptDock 把作者已有的论文变成可检查、可投稿、可返修、可追溯和可发布的完整成果包。

完整成果包不是产品终点，而是学术知识体的第一次可交付快照。ManuscriptDock 的根本
目标是让论文从投稿前开始就成为由作者控制、带来源和版本、可被机器理解、可与 AI
协作并可按授权进入学术传播网络的知识体。

它不是从空白页开始的通用论文编辑器，也不是上传论文后给出一个 AI 分数的网站。它位于作者完成主要写作之后、论文进入学术传播网络之前，并持续管理投稿、审稿和返修过程。应用内只提供围绕投稿问题的结构化修订，不替代 Word 或 Overleaf。

因此，“投稿工作台”是近期产品形态，“个人学术知识体入口”是长期产品定位。前者用于
建立高频价值和数据信任，后者决定数据模型、版本体系、开放协议与 PWC 对接方向。

从服务模型看，用户和付费者是作者、团队与机构，平台持续服务的核心对象是学术知识体。
所有正式功能都应读写同一个知识体，而不是形成互不关联的工具结果。详见
[学术知识体服务模型](knowledge-body-service-model.md)。

## 2. 名称语义

`Manuscript` 指正在创作、投稿、审稿、返修或等待出版的学术稿件；`Dock` 表示稿件在正式交付前停靠、整理、检查、装配和发出的位置。

推荐公开表达：

- 品牌：ManuscriptDock；
- 中文品牌：投稿舱；
- 类别说明：论文投稿工作台；
- 核心口号：从论文初稿到完整投稿包。

代码、安装包、窗口标题、设置页面和公开文档统一使用 `ManuscriptDock`。中文市场可以显示“投稿舱 ManuscriptDock”，不将 `Manuscript` 直译为“手稿”。

PWC 暂时表示未来的机构中央端及内部项目代号，不作为 ManuscriptDock 的公开前缀；正式对外前需要单独完成中央端品牌命名。

## 3. 目标用户

### 3.1 首要用户

正在准备期刊或会议投稿、使用 Word 或 LaTeX 写作的个人研究者，包括研究生、青年教师、临床研究者和独立作者。

他们通常已经拥有论文内容，但面临规则分散、材料重复、版本混乱和返修难追踪的问题。

### 3.2 次要用户

- 同时管理多篇论文的课题组负责人；
- 需要落实机构投稿规范的科研管理人员；
- 协助作者处理格式、语言和投稿材料的专业人员；
- 通过 PWC 机构中央端提供评审、治理和发布服务的组织。

首版仍以单机个人作者为中心，不因为未来 B 端需求而提前增加复杂的组织后台。

## 4. 用户任务

作者使用 ManuscriptDock 不是为了“管理知识网络”，而是为了完成以下任务：

1. 确认论文离投稿还差什么；
2. 针对目标期刊或会议生成完整投稿材料；
3. 在不破坏原稿的前提下修复格式和完整性问题；
4. 清楚知道哪些内容仍在本地、哪些内容将被外发；
5. 必要时请求可信的专业评审；
6. 收到审稿意见后逐条返修并形成回复；
7. 找回任何一次实际提交的版本和材料；
8. 在作者确认后发布预印本或结构化论文知识体。

## 5. 产品价值层级

产品按信任建立顺序提供价值：

| 层级 | 用户获得的价值 | 信任要求 |
| --- | --- | --- |
| 立即价值 | 本地解析、健康度概览、排版预览 | 低 |
| 确定价值 | 生成投稿包、规则检查、图表与引用核对 | 低到中 |
| 持续价值 | 版本保险箱、审稿意见与返修管理 | 中 |
| 专业价值 | PWC 专业评审 Agent | 高，必须明确外发 |
| 网络价值 | 预印本和论文知识体发布 | 高，必须由作者确认 |

“专业自动排版”是进入产品的抓手，“完整投稿包”是第一核心结果，“返修管理”是回访抓手，“专业评审”是后续高价值服务。

所有层级必须沉淀到同一个学术知识体：源稿、结构、论点、证据、图表、引用、声明、
规则结论、评审意见、作者回应、投稿快照和发布标识都保留来源关系。不能为了快速加入
聊天或排版功能而建立无法回写知识体的旁路数据。

## 6. 产品原则

### 6.1 本地优先

首次导入和基础检查无需注册或上传。未发表论文、审稿材料和作者身份默认保存在本地。

### 6.2 非破坏性

原始文件永不被自动覆盖。每个目标、转换、评审和投稿动作都生成独立版本或不可变快照。
作者修改稿进入本地论文版本库：内容变化才创建新版本，重复内容不制造版本；恢复旧稿
通过创建新版本完成，不移动或删除已有历史。详细语义见[本地论文版本库](local-version-library.md)。

### 6.3 外发透明

任何远程模型、专业评审或发布行为都说明发送内容、接收方、目的和版本，并在执行前获得用户确认。

### 6.4 确定性优先

先解决能依据公开规则验证的问题，再呈现主观的 AI 建议。系统必须区分“违反规则”“建议改进”和“需要作者判断”。

### 6.5 解释和恢复

自动操作必须给出依据、差异和撤销能力；错误必须说明恢复路径。不能用一个不可解释的总分替代问题详情。

### 6.6 连接而非替代

首版连接 Word、LaTeX、Zotero、CSL 和预印本生态，不从头替代写作与文献管理工具。

### 6.7 规则组合而非模板堆积

ManuscriptDock 不为每本期刊复制一套完整 Word 或 LaTeX 模板。系统先把论文解析为统一结构，再组合国家标准、出版商、期刊、文章类型和投稿阶段规则。期刊层只保存相对于上层规则的差异。

完整方案见 [投稿规则系统](submission-rule-system.md)。

### 6.8 知识体连续性

每项功能都必须回答“它为论文知识体新增了什么可追溯信息”。界面可以保持简单，但
底层对象需要稳定标识、版本、来源、关系和权限。AI 输出默认是带来源的候选结论，不能
直接覆盖作者事实；外部发布默认是知识体某一版本的授权投影，不能反向替代本地原本。

完整演进方案见 [学术知识体演进路线](academic-knowledge-body-roadmap.md)。

### 6.9 修订即新版本

检查结果必须能够进入“查看依据—修改或接受—确认差异—保存新版本—重新检查”的闭环。
投稿优化修订台记录改了什么、为什么改以及由谁确认；本地论文版本库保存由此形成的
不可变文件和父子关系。二者共同服务知识体演化，不建立脱离版本来源的临时编辑副本。

修订台只处理投稿所需的结构化字段和正文区块，不扩张为通用 Word 替代品。详细设计见
[投稿优化修订台](submission-revision-desk.md)。

投稿前检查的竞争基线、与 Paperpal 等同类产品的差异化原则和市场传播边界见
[Paperpal 竞争应对与市场定位](competitive-positioning-paperpal.md)。

## 7. 信息架构

### 7.1 应用级结构

```text
ManuscriptDock
├── 论文
│   ├── 最近使用
│   ├── 进行中
│   └── 已归档
├── 当前任务
│   ├── 待确认问题
│   ├── 返修事项
│   └── 外发与发布任务
└── 设置
    ├── 本地存储
    ├── 模型与服务
    ├── PWC 连接
    ├── 隐私与网络
    └── 更新与关于
```

“投稿包”“评审”和“返修”主要属于一篇论文的内部阶段，不在全局侧栏重复建立三个互相割裂的文件库。

### 7.2 单篇论文结构

```text
论文概览
├── 稿件与附件
├── 本地版本库
├── 投稿目标
├── 投稿优化修订台
├── 投稿包
├── 专业评审
├── 审稿意见与返修
├── 版本与提交记录
└── 发布
```

## 8. 首版核心流程

首版顶级阶段固定为：`导入 → 检查 → 修订 → 版本 → 期刊匹配 → 存证 → 投稿 → 知识体`。完整状态
合同、恢复和失效语义见[端到端论文生命周期](end-to-end-manuscript-lifecycle.md)。

### 8.1 第一次使用

1. 打开应用；
2. 拖入 DOCX、LaTeX 项目或 PDF；
3. 本地解析、选择目标规则并完成投稿检查；
4. 用户根据逐条依据确认或修复；
5. 查看差异并保存为新的不可变版本；
6. 自动复查当前版本并核验版本差异；
7. 保存姓名、学校/机构、学院或专业、论文用途和截止日期；检索并核验适用的学校正式规则，
   再基于当前版本、规则版本和公开目录快照计算国内、国际各 3 个投稿候选；
8. 作者确认当前版本和检查报告，生成本地存证；
9. 导出投稿交付包，由作者在期刊系统提交后登记回执；
10. 固化这次生命周期的知识体快照。

首次流程不要求用户理解知识体、Agent、规则包或数据协议。只有当功能需要时，才解释这些概念。

### 8.2 专业评审

基础问题处理后，系统可以建议专业评审，但不能阻止用户直接导出。评审前展示外发清单和快照；评审结果回到本地并与具体段落、图表和证据关联。

### 8.3 返修

用户导入决定信或审稿意见，系统拆分条目、关联位置、追踪状态、对比版本并组织回复信，最终重新生成投稿包。

## 9. 首版屏幕清单

### P0：完成闭环必须具备

1. 首次进入与导入；
2. 论文列表；
3. 论文概览；
4. 投稿目标选择；
5. 文档预览与问题面板；
6. 投稿包内容与生成进度；
7. 导出和提交快照；
8. 外发确认；
9. 审稿意见列表；
10. 返修与回复工作区；
11. 版本历史；
12. 隐私、网络和模型设置。

P0 修订能力首先覆盖标题、摘要、关键词、作者单位和投稿声明等确定性字段；正文区块、
逐词红线和 DOCX/TEX 安全往返按阶段扩展。修订台的完整范围以
[投稿优化修订台](submission-revision-desk.md)为准。

规则覆盖从通用能力开始：任何期刊都可以使用基础投稿准备；首版只为少量主要出版商和首批用户高频目标提供经过核验的增强规则，不承诺覆盖全球所有期刊的最终出版版式。

### P1：闭环验证后扩展

- Zotero 深度连接；
- 多目标转投；
- 预印本连接器；
- PWC 组织任务；
- 共同作者确认；
- 结构化论文知识体预览。

### 暂不进入首版

- 完整在线协作编辑器；
- 可替代 Word 或 Overleaf 的通用全文编辑器；
- 大规模学术知识图谱浏览；
- 通用文献管理器；
- 期刊社编辑后台；
- 自动替作者执行不可逆投稿或发布。

## 10. 产品语言

优先使用作者熟悉的任务词，而不是内部技术词：

| 使用 | 避免作为默认界面文案 |
| --- | --- |
| 导入论文 | 摄取知识对象 |
| 生成投稿包 | 编译 Artifact Package |
| 检查问题 | Agent Evals |
| 专业评审 | 远程智能体调度 |
| 保存提交版本 | 固化不可变对象快照 |
| 将发送给… | 调用外部模型端点 |

专业概念可以出现在详情和审计记录中，但不应成为首次使用门槛。

## 11. 体验基线

主界面遵循 [ManuscriptDock 设计系统](../design-system/manuscriptdock/MASTER.md)：极简、文档优先、状态透明、键盘可达，并支持触控与未来 iOS 伴随端。

视觉与交互参考 OpenAI 产品的简洁方式：中性色、充足留白、内容居中、单一主输入和渐进披露；叠加学术工作所需的文档预览、规则依据、版本与隐私状态。参考的是体验原则，不复制 OpenAI 的商标、图标或具体界面资产。

早期知识观测 Demo 的科幻数据界面属于未来知识分析模块，不延续到投稿工作台的核心流程。
